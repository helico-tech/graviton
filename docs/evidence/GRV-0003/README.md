# GRV-0003 evidence — deterministic transcendental kernels

2026-09-17, branch `GRV-0003-kernels`. Node v24.14.0, CPython 3.12.3 (the
versions actually installed here, matching ADR-0005's "Node 24 in both
CPython 3.12 and Node 24").

## Port derivation

`src/sim/math/kernels.ts` is a line-for-line port of the kernels section of
`docs/research/2026-09-03-02-simulation-numerics-probes/q1_core.mjs`
(hashing/rng are GRV-0004's, Kepler is GRV-0005's — neither is touched here).
Two deliberate deviations from the reference:

- **Raw bit access via `DataView`** (`hiWord`/`loWord`/`fromWords`), not the
  runtime-endianness-detected `Float64Array`/`Uint32Array` alias the
  reference uses. Same reasoning and same technique as
  `src/sim/state/hash.ts` (see `docs/evidence/GRV-0004/README.md`):
  `DataView.setFloat64`/`getUint32` fix big-endian byte order explicitly, so
  no `LE` runtime probe is needed.
- **`PI_LO` is written as `1.2246467991473532e-16`**, not the reference's
  `1.22464679914735317700e-16`. Both parse to the identical double
  (`1.22464679914735317700e-16 === 1.2246467991473532e-16` in Node); the
  shorter form is required because ESLint's `no-loss-of-precision` rule (part
  of `js.configs.recommended`, already in `eslint.config.js`) flagged the
  22-digit form as ambiguous. No other coefficient triggered it — checked by
  running `pnpm lint` to completion, not by inspection, since most of this
  file's other fdlibm constants also carry >17 written digits that happen to
  round-trip exactly.

Everything else — every coefficient, the medium-path `__ieee754_rem_pio2`,
the `kSin`/`kCos` kernels, the four-region `datan`, `datan2`'s branch
structure, `dacos(x) = datan2(sqrt((1-x)(1+x)), x)`, `dexp`'s `k*ln2`
splitting, `dlog`'s `s = f/(2+f)` kernel, and `pow2i`'s exponent-field
construction — is an unchanged port. `dsincos` keeps the reference's
exported-mutable-output-variable shape (`dsinOut`/`dcosOut`, written by
`dsincos(x)` rather than returned) instead of allocating a pair or an object:
GRV-0005's Kepler solver calls it three times per ephemeris query, the only
high-frequency trig in the simulation, and this matches the
mutate-in-place convention `src/sim/state/rng.ts`/`hash.ts` already use for
hot-path state.

`dsin`/`dcos`/`dsincos` throw `RangeError` for `|x| > 2^18` — the sim's own
contract (research §2.2: mean anomaly is always pre-reduced into `[0, 2pi)`,
so no real caller needs a wider domain), stricter than the medium-path
reduction's actual `|x| < 2^19 * pi/2 ≈ 8.2e5` validity. This guard has no
counterpart in the reference; it is new in the port.

## Golden vectors: derivation

**The 18 cross-runtime bit patterns** (research §2.6) were re-measured in
this environment rather than copied from the research doc, by running the
probes directly:

```
$ node docs/research/2026-09-03-02-simulation-numerics-probes/q2_selftest.mjs
$ python3 docs/research/2026-09-03-02-simulation-numerics-probes/q3_crosscheck.py
  All bit patterns identical across runtimes: True
```

All 18 matched, identical to the values recorded in the research doc, on
Node v24.14.0 / CPython 3.12.3. `kernels.test.ts` embeds 15 of them directly:
the 12 `dsin`/`dcos` values and `dexp(2.5)`/`dlog(7.5)`/`datan2(3,-4)`,
asserted against the exported kernels.
>
> **UPDATED 2026-09-17 (GRV-0005):** the remaining 3 (Kepler `E`, `sinE`,
> `cosE` for `M=1, e=0.6`) were originally asserted here by reproducing the
> Danby-solver arithmetic *inside this test*, since `solveKepler` didn't exist
> yet. They now live in `src/sim/ephemeris/kepler.test.ts`, asserted against
> the real exported `solveKepler` (GRV-0005) rather than a copy — a stronger
> test than the original, and the reason this file no longer contains a
> from-scratch Danby solve.

**The `<=2ulp` accuracy grid** (92 values across `dsin`/`dcos`/`datan`/
`dacos`/`datan2`/`dexp`/`dlog`) was generated by reusing `p3_dtrig.py`'s
already-validated 70-digit `decimal.Decimal` reference functions
(`dec_sin`/`dec_cos`/`dec_atan`/`dec_exp`/`dec_log`, which convert each float
input exactly via `Decimal(x)`, never through `repr()` — the bug the research
doc's §2.3 already warns cost the first run of that probe): for each grid
point, `float(reference_fn(Decimal(x)))` gives the correctly-rounded double,
recorded as a big-endian hex bit pattern
(`struct.pack('>d', v).hex()`), and `kernels.test.ts` asserts
`ulpDistance(ours(x), thatDouble) <= 2` using the standard
bits-to-monotonic-ordering ULP technique (Bruce Dawson), never `Math.*`. The
generation script is not part of the repo (throwaway, run from the worktree
against `p3_dtrig.py`); reproducing it is one Python invocation against
already-committed research code.

## Measured accuracy

Re-run in this environment (`python3 p3_dtrig.py`, ranges as in research §2.3):

| function | range | N | max rel err | max ulp |
|---|---|---|---|---|
| `dsin`/`dcos` | `[-pi/4, pi/4]` | 4000 | 1.460e-16 | 1.062 |
| `dsin`/`dcos` | `[-2pi, 2pi]` | 4000 | 1.829e-16 | 1.167 |
| `dsin`/`dcos` | `[0, 200]` | 4000 | 2.019e-16 | 1.292 |
| `dsin`/`dcos` | `[0, 1e4]` | 4000 | 1.455e-16 | 1.097 |
| `dsin`/`dcos` | `[0, 1e5]` | 4000 | 1.547e-16 | 1.070 |
| `dsin`/`dcos` | `[0, 8.2e5]` | 4000 | 1.494e-16 | 1.061 |
| `dsincos` | `[0, 2pi)` | 4000 | 1.690e-16 (rel) | — |
| `datan2` | exponents ±30 | 6000 | 2.514e-16 | 1.549 |
| `dexp` | `[-8, 8]` | 6000 | 1.346e-16 | 0.859 |
| `dlog` | `[2e-9, 5e8]` | 6000 | 1.279e-16 | 0.713 |
| `dlog` | `[1, 30]` | 6000 | 1.383e-16 (rel) | — |
| `datan` | `[-1000, 1000]`, all 4 regions | 6000 | 1.050e-16 | 0.535 |
| `dacos` | `[-1, 1]`, dense near ±1 | 4028 | 2.574e-16 | 1.375 |

`datan`/`dacos` aren't in `p3_dtrig.py` (it only measures `datan2`); measured
separately by calling its own `dec_atan` reference the same way, dense
sampling near `x = ±1` for `dacos` since that's where the
`(1-x)*(1+x)` construction is specifically meant to hold precision. Every
function stays under the 2 ulp acceptance bar with headroom; worst case
(`datan2` at 1.55 ulp) matches the research doc's own measurement exactly.
